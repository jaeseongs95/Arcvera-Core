# Arcvera-Core 인덱스 기반 컨텍스트와 증분 압축

[English](context-index.md) · [한국어](context-index.ko.md)

R41은 현재 대화에 호스트가 관리하는 밴더 독립적인 인덱스를 도입합니다. 원문을 인덱스에 복사하지 않고 출처 ID, 작업 수명, 의존관계, 활성 제외 이력을 기록합니다. 이 문서는 개발 후보의 설계를 설명합니다. 최종 실행본 동작·성능·릴리스 수용 여부는 [R41 릴리스 노트](releases/R41.md)에 근거가 기록될 때까지 미검증입니다.

## 데이터와 권한

| 기록 | 의미 |
| --- | --- |
| 출처 | 원래 response-item ID 또는 기존 도구 항목의 호출·결과 locator, 종류, turn, 순서, 선택적인 소유 작업 |
| 작업 | 명시적 ID, 이름, `active` 또는 `completed` 상태, 의존 작업 ID |
| 리비전 | 비교 후 교환 방식의 갱신에 사용하는 단조 증가 정책 리비전 |
| 감사 이벤트 | 해당 리비전에서 수용한 연산과 활성 제외·재활성화한 출처 ID |

원문은 기존 대화 저장소에 남습니다. 인덱스 메타데이터와 조회한 과거 내용은 권한을 부여하거나 현재 사용자 지시를 대체하지 않으며, 요청에 대한 승인을 증명하지 않습니다. 호스트가 외부 메모리 조회를 비활성화한 경우 그 상태를 유지합니다. 이 도구는 외부 메모리, 임의 파일, 다른 대화를 조회하지 않습니다. 조회 불가는 관련 정보가 없다는 근거가 아닙니다.

## 활성 문맥 구성

출처를 등록할 때 직렬화한 원문의 SHA-256 동일성 근거를 저장하며, 인덱스에 본문을 복사하지 않습니다. 같은 locator에 다른 본문이 들어오거나 기존 descriptor에 동일성 근거가 없으면 해당 출처를 알 수 없는 종류로 바꾸고 보수적으로 재활성화합니다. 압축 시 같은 ID의 새 항목이 남아 있어도 서로 다른 원문은 모두 보존합니다. 이 처리로 모델 입력이 커질 수 있으며, 해시가 의미적 동등성이나 원문 폐기 권한을 부여하지는 않습니다. 해시 계산 비용은 원문 크기에 비례하며 프로세스 전체 메모리 상한을 제공하지 않습니다.

원문 식별과 모델 입력용 본문 식별은 구분합니다. `body_sha256`은 직렬화한 원문을, 선택적인 `projection_sha256`은 호스트가 준비한 메모리 내 본문을 식별하며 도구 결과가 잘린 형태일 수 있습니다. 체크포인트는 해당 본문과 locator·종류·호출 ID·호스트 압축 출처 범위가 일치할 때 알려진 출처의 분류를 유지할 수 있습니다. 새 원문 수집은 항상 원문 식별을 검사하므로, 새 원문이 과거의 잘린 본문과 같아도 과거 원문으로 간주하지 않습니다. 원문 해시가 없거나 원문이 충돌하면 알 수 없는 종류로 활성 상태를 유지합니다. ID 없는 체크포인트 항목은 출현 횟수에 맞춰 대조하며, 동일한 반복 항목 여러 개를 descriptor 하나로 처리하지 않습니다.

작업을 시작할 때 필요하면 `create_task`로 생성하고 `set_focus`로 현재 작업을 선택합니다. 모델 API 요청에는 선택한 작업과 의존관계를 따라 도달하는 작업의 상세 내용을 유지합니다. 관련 없는 작업은 활성 상태여도 분류된 상세 내용을 제외합니다. 완료된 의존 작업도 현재 작업이 참조하면 유지합니다. 현재 작업을 완료해도 다른 작업이 자동 선택되지는 않으므로 다음 focus를 명시해야 합니다. 원래 이력과 권한 검토 근거는 이 모델 입력용 구성과 구분합니다.

사용자 메시지, system/developer 제어, 알 수 없는 종류, 미분류 항목, 안정적인 locator가 없는 기존 항목은 활성 상태를 유지합니다. 지시 만료를 추정하지 않으므로 최신 사용자 정정도 유지합니다. focus를 선택하지 않은 경우에는 활성 작업의 참조 폐포와 미분류 내용을 보수적으로 유지합니다. 이 기존 대화 모드가 보유한 모든 항목의 현재 작업 관련성을 증명하지는 않습니다.

새 assistant·도구 상세 내용은 알려진 현재 focus에 연결합니다. 호스트가 생성 출처를 확인한 새 추론·압축 항목도 해당 focus를 따르며, 기존의 불투명한 내용은 보수적으로 유지합니다. 도구 호출과 결과는 하나의 그룹으로 취급합니다. 불완전한 그룹은 활성 상태를 유지하며, 구성원 하나를 작업에 연결하면 그룹 전체를 같은 작업에 연결합니다. 출처를 다른 작업으로 조용히 옮길 수 없습니다. 명확히 성공한 네이티브 `context_index` apply의 완료된 호출·결과 그룹만 모델 재전송에서 제외해 갱신 인자의 무관한 작업 메타데이터가 반복 노출되지 않도록 합니다. 실패·진행 중·read·list·audit 그룹은 통상 보존 규칙을 유지합니다. 일반 CodeMode 실행을 추정으로 성공한 네이티브 apply로 취급하지 않습니다. 원시 이력·감사·권한 근거는 보존합니다.

Sampling·prewarm·로컬 및 원격 압축은 같은 문맥 구성을 사용하도록 연결하는 것이 목표입니다. 인덱스 정책 리비전이 바뀌면 캐시한 WebSocket `previous_response_id` 연결 문맥을 무효화해 서버의 이전 문맥이 제외한 상세 내용을 되살리지 않도록 합니다. 정책이 같으면 다른 조건이 충족되는 한 기존의 연결 문맥 최적화를 유지합니다. 새 전송 연결을 열 때는 연결·이어받기 상태를 초기화하되 연결된 정책 리비전과 인증 소유자 세대는 유지합니다. 재연결 때문에 같은 정책을 다시 정책 변경으로 판단해서는 안 됩니다. 전경·백그라운드 압축은 이전 정책에서 캡처한 결과의 채택을 거부해야 합니다. 현재 사용자·제어·미분류 출처는 요약과 별도로 보존하며, 이들의 누적으로 문맥 절감에 한계가 있습니다. 통상적인 활성 제외는 전체 대화 요약 요청 없이 인덱스 갱신으로 처리합니다. 활성 입력을 더 압축해야 할 때는 기존 요약 압축을 유지합니다. R41은 새로운 의미 요약 형식, 자동 지시 만료 추론, 프로세스 전체 메모리 상한을 제공하지 않습니다.

구현은 활성 여부·도달 가능한 작업·메모리에 남은 출처 위치를 유지합니다. 보유 원문 전체를 복사한 뒤 거르는 대신 활성 위치를 선택해 모델 입력을 구성합니다. 정책 변경은 여전히 원문 없는 인덱스 상태를 복제하고 파생 집합을 다시 구성하며, 인덱스·감사 이력은 대화에 따라 증가합니다. 크기가 제한된 요청 전용 탐색 메타데이터로 참조 작업과 현재 메모리 범위 밖의 활성 출처를 안내합니다. 필요한 원문은 `read`로 확인한 뒤 사용해야 합니다. 모든 보관 출처의 자동 복원이나 물리 메모리 회수를 뜻하지 않으며 전체 경로의 지연·메모리 개선은 실제 측정이 필요합니다.

## 네이티브 도구 계약

`context_index`는 대화에서 사용하는 네이티브 도구이며 PowerShell 명령이나 슬래시 명령이 아닙니다. 요청은 정의된 필드만 허용하는 JSON 객체입니다. 지원하지 않는 필드와 잘못된 값은 오류로 처리합니다.

| 동작 | 입력과 결과 |
| --- | --- |
| `list` | 선택적인 음이 아닌 `cursor`, 1~100의 `limit`(기본 25), `include_unrelated`(기본 false). 리비전, focus, 출처·작업 메타데이터, 활성 이유, 전체·표시 개수, 캐시 메타데이터, 복구 상태, `next_cursor` 반환 |
| `read` | 현재 대화의 정확한 `source_id`, 선택적인 바이트 `offset`, 1~16384의 `max_bytes`(기본 8192). 직렬화한 `ResponseItem` JSON을 UTF-8 경계에 맞춰 나누고 `next_offset` 반환 |
| `apply` | 필수 `expected_revision`, 1~128개의 `operations`. 일괄 연산 전체를 검증·수용하거나 오류 반환 |
| `audit` | 선택적인 음이 아닌 `cursor`, 1~100의 `limit`(기본 25). 이벤트 요약·개수와 `next_cursor` 반환. 정확한 이벤트 `revision`을 지정하면 `offset`·`max_bytes`(기본 8192, 최대 16384)로 원래 JSON을 UTF-8 경계에 맞춰 나눠 반환 |

focus를 선택한 경우 `list`는 기본적으로 활성 출처와 도달 가능한 작업을 표시합니다. `include_unrelated: true`로 보관·무관 항목의 메타데이터 탐색을 명시적으로 확장할 수 있지만 focus를 바꾸거나 원문을 자동 조회하지는 않습니다. 같은 cursor로 출처와 작업을 각각 인덱스 키 순서에 따라 페이지 단위로 반환합니다. `audit`는 수용한 이벤트 요약을 순서대로 반환하며 바이트 offset에는 이벤트 revision이 필요합니다. 반환된 cursor·offset으로 계속 조회합니다. 여러 페이지를 확인하는 동안 인덱스 리비전이 바뀌면 판단 전에 현재 상태를 다시 확인합니다. 요청과 직렬화한 응답은 각각 65536바이트 이하로 제한하며 필요한 경우 페이지 크기를 줄입니다.

| 연산 | 필수 필드 |
| --- | --- |
| `create_task` | `task_id`, `label` |
| `bind_sources` | `task_id`, `source_ids`(알려진 정확한 ID 1~1024개) |
| `set_task_state` | `task_id`, `state`(`active` 또는 `completed`) |
| `add_dependency` | `task_id`, `dependency_id`(모두 기존 작업) |
| `remove_dependency` | `task_id`, `dependency_id`(기존 관계) |
| `set_focus` | `task_id`(요청 문맥의 시작점으로 선택할 기존 작업) |

작업 ID는 UTF-8 기준 1~256바이트이며 제어 문자를 허용하지 않습니다. 이름은 최대 1024바이트입니다. 의존관계에는 방향이 있습니다. 현재 focus A가 B에 의존하면 B의 완료 여부와 관계없이 B와 B의 의존 작업을 유지합니다. 순환 의존관계에서도 탐색은 종료합니다. 관련 없는 순환 집합이 스스로 도달 가능해지지는 않습니다. focus가 없을 때는 활성 작업을 보수적인 시작점으로 사용합니다.

새 인덱스에서 다음과 같이 일괄 연산할 수 있습니다.

```json
{"action":"apply","expected_revision":0,"operations":[{"op":"create_task","task_id":"investigation","label":"Investigate the reported failure"},{"op":"create_task","task_id":"repair","label":"Repair and verify"},{"op":"add_dependency","task_id":"repair","dependency_id":"investigation"},{"op":"set_focus","task_id":"repair"}]}
```

실제로는 `list`가 반환한 리비전을 사용하고 현재 대화에서 반환한 출처 ID만 연결합니다. `investigation`을 완료해도 현재 focus인 `repair`가 의존하면 제외 가능한 상세 내용을 유지합니다. 무관한 작업의 분류된 상세 내용은 활성 상태여도 제외합니다. 사용자·제어 출처는 완료 여부와 관계없이 보호합니다. 이 예시 자체는 수정 실행 권한을 부여하지 않습니다.

`read`는 현재 대화의 저장소만 사용하며, fork 상속도 저장소가 허용한 범위에 한정합니다. 임시 대화에서는 메모리에 남은 이력만 조회할 수 있고 이미 잘렸을 수 있습니다. 결과에는 이 저장 경계가 표시됩니다. 알 수 없는 ID, 원문 부재, 안정적인 locator가 없는 기존 항목, 잘못된 UTF-8 offset, 저장소 오류는 명시적인 실패입니다. 같은 출처의 동일한 원문이 반복되면 조회할 수 있습니다. 같은 locator가 서로 다른 원문을 가리키면 명시적인 모호성 오류를 반환하고 모든 원문을 보존합니다. 원문을 요약으로 대체하거나 조회 실패를 정보 부재로 해석하지 않습니다.

저장된 원문의 조회는 전체 이력 API나 표시용 페이지 API와 독립적으로 동작해야 합니다. 페이지 방식 fork의 조회는 보관·압축된 상위 대화를 포함해 고정된 상속 바이트·순번 범위를 지키고, 압축 기록을 지나 조회하되 대체 본문을 원문으로 취급하지 않아야 합니다. 손상된 기록, 파일 접근 불가와 취소는 명시적인 실패로 유지해야 합니다. 로컬 조회의 I/O 비용은 허용된 이력 바이트 수에 비례하며, 선택한 원문과 가장 큰 디코딩 기록을 메모리에 유지합니다. 압축 입력에는 익명 임시 디코딩 파일이 필요할 수 있습니다. 응답 조각 크기 제한은 프로세스 전체 메모리 상한이 아닙니다. 릴리스 수용 전에 이 경계의 최종 네이티브 검증이 필요합니다.

## 영속화·이전·복구

Arcvera-Core는 자체 컨텍스트·저장 계약을 관리합니다. 공식 Codex CLI와의 호환성은 지원 범위에서 제외합니다. OpenAI 서버 통신과 이에 필요한 서버 API·인증 경로는 지원합니다. 소스 출처 표시나 저장된 원문 보존은 공식 CLI와의 상호 교체를 보장하지 않습니다.

정책 변경은 대화 checkpoint·설정과 같은 영속화 순서 경계를 사용합니다. 수용한 트랜잭션은 도구 대기가 취소돼도 자체 수명을 유지합니다. 이벤트를 먼저 기록한 뒤 해당 리비전을 현재 인덱스에 반영합니다. 기록 결과가 불확실하거나 현재 상태 반영에 실패하면 명시적인 복구 오류가 됩니다. cold resume으로 저장 상태를 해소하기 전에는 새 sampling·정책 변경·압축을 계속하지 않아야 합니다. 응답 항목 기록에 실패하면 영속화 직렬화 경계를 해제하기 전에 복구 오류를 표시해, 후속 정책 변경이 저장되지 않은 출처를 연결하지 못하도록 합니다. 일부가 저장됐을 가능성이 있으므로 원래 이력은 보존합니다. 결과가 불명확한 요청을 자동 재전송하지 않습니다. 복구 후 `list`·`audit`를 확인하고 다음 행동을 정합니다.

압축 재개 메타데이터에는 원문 없는 인덱스 snapshot을 저장할 수 있으며, 후속 정책 이벤트에는 기대 리비전과 새 리비전이 포함됩니다. 복원 시 참조를 검증하고 파생 집합을 다시 구성합니다. 리비전 불일치나 잘못된 참조는 오류이며 메타데이터를 조용히 버릴 근거가 아닙니다. 이력을 파괴적으로 교체할 때는 교체 이력에서 다시 구성해 폐기한 작업 연결을 되살리지 않습니다. 실제 resume·fork·rollback·동시 압축·실패 복구 경계는 최종 후보에서 실행시험이 필요합니다.

Core 체크포인트 복원과 로컬 저장소 이관은 같은 descriptor 대조 규칙을 사용합니다. 일반 snapshot에서 메모리에 남은 native/call 출처가 빠졌다면 이전 인덱스의 원문 descriptor를 기준으로 보완합니다. 잘린 본문을 새 원문으로 간주하거나 새 focus에서 소유 작업을 추정하지 않습니다. 알 수 없는 출처는 활성 상태를 유지합니다. 실제 rollback이나 파괴적 이력 교체는 살아남은 이력으로 새 인덱스를 만들며 폐기한 작업·focus·보관 출처·동일성 근거를 초기화합니다. 이 초기화는 압축 체크포인트 복원과 구분합니다.

인덱스 메타데이터가 없는 기존 대화는 등록한 출처를 활성 상태로 유지하는 것이 안전한 시작 상태입니다. 이전 과정에서 완료 작업을 추정하거나 원문을 삭제하지 않습니다. 기존에 압축된 대화의 승인된 저장소에 원문이 이미 없다면 복원할 수 없습니다. R41은 raw fallback, 강제 reset, 자동 인증, 다른 대화를 통한 복구 조회를 도입하지 않습니다.

승인된 설치·공유 서버 전환 전에는 이전 전체 패키지를 보관하고 대화·인증 저장소를 보존합니다. 새 context-index rollout 기록과 checkpoint 필드를 이전 실행본이 읽을 수 있는지는 검증되지 않았습니다. EXE를 되돌리는 것만으로 R41이 변경한 대화의 하위 버전 복구가 검증되지는 않습니다. 새 기록을 보존하고 비호환 reader 오류가 발생하면 중단합니다. 격리 사본과 호환되는 reader로 복구를 시험하며, 구버전으로 열기 위해 운영 저장소를 편집하거나 기록을 삭제하지 않습니다. 설치·운영 전환은 발행과 별개의 작업입니다.

## 캐시 관측과 보관 기간

네이티브 `list`는 가장 최근에 완료한 sampling 응답의 캐시 관측을 제공합니다. `input_tokens_details.cached_tokens`가 음이 아닌 정수로 제공되면 양수는 응답 단위 `hit`, 0은 `miss`입니다. 값이 없거나 null이면 `unknown`이며, 잘못된 자료형·음수·정수가 아닌 값·제공된 입력 토큰 수의 잘못된 자료형·입력 토큰 수보다 큰 캐시 수치는 `invalid`입니다. 누락 지표를 0으로 바꾸지 않습니다. 합계 캐시 토큰 수는 어떤 출처·작업·지시·원문이 캐시에 적중했는지 알려주지 않습니다.

`observed_at`은 호스트가 sampling 완료를 관측한 시각이며 서버의 캐시 생성 시각이 아닙니다. `request_context_index_revision`은 해당 요청에서 캡처한 값입니다. `current_context_index_revision`과 `revision_status`로 현재·과거·불명의 관측을 구분합니다. 늦게 도착한 결과를 새 정책 리비전의 결과로 바꾸지 않습니다. 현재 관측 범위는 sampling이며 compaction·prewarm은 `not_observed`입니다.

보관 기간과 만료 시각은 `unknown`, 출처는 `not_provided`, 값은 null로 유지합니다. adapter가 확인한 TTL·만료 경로는 구현하지 않았으며 임의 usage 필드나 추정한 제공자 기본값을 서버 보장으로 승격하지 않습니다. 향후 설정값·추정값을 추가하면 서버 확인 근거와 구분해야 합니다. 캐시 상태는 관련성·권한·원문 및 필수 문맥 삭제를 결정하지 않습니다. 관측 시각은 메타데이터를 명시적으로 조회할 때 반환하며 요청 탐색 manifest에 자동 삽입하지 않습니다.

## 검증 의무

릴리스는 각 주장을 실제 sampling·압축·네이티브 도구·영속화 경로 시험과 연결해야 합니다. 직렬화한 HTTP·WebSocket payload의 현재 작업 필터, 완료됐지만 참조 중인 출처, 무관한 활성 작업과 이름, 전이·순환 의존관계, 최신 사용자 정정·권한 근거, 불완전한 호출·결과 그룹, 성공한 네이티브 apply 메타데이터 재전송, 오래된 리비전·실패한 일괄 연산의 원자성, 크기가 제한된 audit·read 출력, 조회 불가능한 원문, UTF-8 조회, 영속 기록 불확실성과 대기 취소, 이전 정책의 전경·백그라운드 압축 채택, 입력이 같아도 정책 변경 시 WebSocket 초기화, 같은 정책의 연결 문맥 유지, resume·fork 복구를 확인해야 합니다. 캐시는 누락·잘못된 값·0·양수, 늦게 도착한 요청 리비전별 관측, 알 수 없는 TTL·만료, 출처별 적중을 알 수 없다는 경계를 확인해야 합니다. 성능 비교는 동일한 부하 조건, 실행본, 활성·전체 출처 수, 경과 시간, 메모리 관측을 명시해야 합니다. 측정이 없으면 미검증입니다.
