# R39 개발 범위와 검증 경계

R39는 공식 0.167.0 기반 R38 소스에서 분기한 개발 작업이다. 이 문서는 소스 작업의 상태를 설명하며 최종 실행 파일, 설치, 릴리스 또는 실제 Desktop 검증 완료를 뜻하지 않는다.

## 추가 요구와 변경

- 훅 명령의 stdout/stderr를 각각 1MiB까지 수집한다. 한도를 초과하면 명시적으로 실패하고 부분 JSON을 반환하지 않는다. 기존 동시 입출력, 전체 시간 제한, 소유 하위 프로세스 정리와 비동기 실행 상한을 유지한다. 사용자가 제보한 훅 현상과 같은 원인인지는 아직 확인하지 못했다.
- `/context inspect`는 이미 실행 중인 현재 대화의 로컬 보관 이력을 역할·항목 종류·메시지 조각의 출처로 집계한다. 원문, 도구 인수, 경로를 응답에 넣지 않는다. 현재 보관 이력은 다음 모델 요청 전체와 다르며, 출처가 확인되지 않은 사용량을 서버 실측으로 표시하지 않는다. 기존 `/context` 한도 조회·설정은 유지한다.
- `/config`에 대화 이력의 마우스 스크롤 감도 선택을 연결한다. 공식 버전에 이미 있는 `tui.mouse_scroll_speed`와 소수 누적 계산을 재사용하며, 현재 사용자 지정 값과 상위 설정의 우선순위를 보존한다. composer·목록의 휠 처리와 실제 Desktop 감도는 별도 경계다.
- 번역 계층을 우회하던 애플리케이션 안내를 한국어 카탈로그로 연결한다. 도구·모델 응답, 경로, 식별자와 기계용 JSON은 보존한다. 카탈로그 키의 일치만으로 모든 실제 화면의 한글화가 검증됐다고 판단하지 않는다.

`codex_tui` 초기화 HTTP 오류에는 이미 재시도가 있다. 현재까지 원인을 확정하지 못했으며, 실행 중인 대화에 다시 연결할 때의 endpoint 수명과 설정 적용 경계를 조사한다. 진행 중 작업을 강제로 종료하거나 재시도 횟수만 늘리는 변경은 하지 않았다.

## 프롬프트 캐싱

R38에는 공식 버전의 캐시 키·접두부 안정화가 이미 있다. 실제 허용된 한 세션의 최근 usage 표본에서는 캐시 사용이 기록됐지만, 이 부분 표본만으로 비용·지연 개선이나 cache miss의 원인을 확정할 수 없다. 일반 usage, 요청·응답 캐시 진단의 활성 상태, 실제 진단 파일 저장은 각각 확인해야 한다.

프로세스 공용 배치는 파일만 보고 한 세션 전용임을 증명할 수 없는 관측 공백이 있다. 이 관측은 R37의 과거 자료이며 R38 효과의 기준 자료로 사용하지 않는다. 사용자의 최신 기준에 따라 R38 app-server가 실제 전환된 뒤 버전·실행 경로·PID와 생성 시각, 실제 요청 생산자의 관측 활성, 세션 귀속과 누락 여부를 확인하고 누적 자료를 분석한다. 그 전에는 캐시 정책이나 원격 관측 구조의 제품 변경을 확정하지 않는다. 다른 R39 개발과 R38 릴리스는 이 자료를 기다리느라 멈추지 않는다.

## 실제 검증과 남은 일

현재까지 작은 독립 시험에서 생산 코드의 훅 읽기·대기 구간, 컨텍스트 집계·DTO·렌더 함수, Fluent 카탈로그를 실제 컴파일하고 실행했다. 이 시험은 변경된 전체 crate, app-server RPC, TUI 이벤트 흐름 또는 실제 Desktop을 실행한 근거가 아니다.

전체 Core·TUI·CLI 컴파일과 회귀 실행, 생성 스키마 갱신, 실제 설정 화면과 입력 snapshot 확인, 실제 RPC의 읽기 전용·경합 검증, 실제 앱 확인, 최종 독립감사와 릴리스는 남아 있다. 원 실패와 미실행 항목을 보존하며 소스 전달 검증을 제품 검증으로 확대하지 않는다.
