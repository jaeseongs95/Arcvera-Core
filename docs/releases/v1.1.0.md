# Arcvera-Core 1.1.0 — Context selection and cache visibility / 문맥 선택과 캐시 가시성

## English

### Overview

This is a pre-release source draft for the Windows x86-64 1.1.0 candidate. Native tests and joint Desktop integration are in progress. The final source identity, executables, package, independent audit and publication have not yet been established. Historical tests are not final 1.1.0 release validation.

### Changes

* Indexed task fragments and dependencies determine the selected context. Unrelated details can leave active model input while originals remain available through authorized retrieval. Request-only navigation follows selected history, preserving its stable prefix when navigation changes.
* With an indexed focus, selected context owns the input budget. If the selection exceeds the model limit, the request reports the limit instead of silently replacing required evidence with a summary. Retrieve smaller original fragments or release unrelated details before retrying.
* Experimental `thread/context/read` returns body-free metadata for a loaded thread using existing connection and runtime access checks. `snapshotId` binds paginated results to one generation; restart on `staleContextSnapshot`. Each serialized page is limited to 65,536 bytes. Resident serialized UTF-8 bytes, local token estimates and provider-reported usage are distinct; unavailable values are null or explicitly unknown. Archive size is not assumed to be zero.
* `hooks/list` distinguishes the current-thread installed runtime from configuration discovery. MCP/hook configuration refresh respects active runtime and policy boundaries; acknowledgement does not establish that an MCP server is ready. Hook stdout and stderr each have a 1 MiB bound; excess output is an error.
* Explicit provider cache policy is optional. For a supporting Responses-compatible provider, configure `[model_providers.<id>.capabilities.prompt_cache]` with `kind = "implicit"` and `ttl = "30m"` or `"12h"`. Alternatively select `kind = "legacy"` and `retention = "in_memory"` or `"24h"` only where supported. With no policy, existing wire behavior is preserved. This does not add a new vendor login or a different wire protocol.
* Requested TTL and reported cache activity do not confirm provider support, application or retention. `minimumValidUntil`, effective TTL, individual fragment TTLs and server-confirmed expiry remain unknown. TTL expiry does not delete originals or change permissions or required selection.

* Optional `requestSizes` describes the latest prepared sampling prompt using four JSON component byte counts: input, base instructions, the standalone tools field, and output schema. The server supplies their sum and the preparation's history/index revisions. Incremental tool definitions carried inside input remain counted in input. This observation can precede the displayed history and does not measure provider normalization, transport envelopes, delta requests, billed tokens or successful delivery. No additional prompt body is retained for these counters.
* TUI MCP registrations belong to their connection and thread subscription. Active work keeps its existing call lifetime; queued replacements apply at the safe runtime boundary. An opaque registration identity links an applied registration to the matching published, connected MCP status. Pending, applied and ready are distinct states. User and managed configuration, authentication, approvals and tool namespaces remain authoritative.
* The candidate supports `--terminal-link-owner=tui|host` for mouse-activated HTTP(S) links. The default is `tui`; use `host` only when the terminal host actually opens those links. File links and URLs opened programmatically for authentication retain their existing handling. A version string alone does not establish support.
* Configuration writes derive their returned user-layer version from the exact serialized document written by that operation. Cooperating writers resolve supported symlink paths to the same target for locking and use the current read for version checks. Empty-layer boundaries and Windows path case behavior are preserved. The lock remains held through a started blocking write after cancellation. Non-cooperating external editors and path replacement after verification remain outside this guarantee.
* Memory consolidation prepares selected inputs in a bounded stage and publishes a verified generation after the existing store's lease, authorization and input checks. Host readers capture one generation. A reset removes the current publication reference while preserving original notes, the managed marker and recovery generations. Managed read failures do not silently fall back to a legacy summary. A generation ID identifies the current captured generation; it does not prove older readers have released their references or that a model's semantic claims are correct.

Core-internal special approval flows require both a Core-issued origin indicator and the existing request checks. External MCP metadata cannot select that origin. Requests from Core 1.0.1 that omit the origin are treated as unknown; their origin must not be used to infer support for special approvals in a newer client. Existing general form and API semantics remain unchanged. Verify that the client and Core versions work together before use. No installation or profile migration is performed automatically.

### Getting started and recovery

In the 1.1.0 TUI candidate, `/context inspect` starts one metadata page of up to 25 fragments. `/context inspect next` requests the next page of the same snapshot; there is no automatic full-history fetch. If a page exceeds the 64 KiB bound, `/context inspect small` restarts with one fragment. An oversized single fragment is reported as unavailable. `/context cancel` cancels presentation of the inspection, while the already-sent request retains its bounded slot until it drains or its connection closes. Existing context-window query, reset and numeric settings remain separate.

Use the complete package from a verified release, including its `bin` folder, package metadata and helpers; keep the previous complete package for recovery. The 1.0.1 [shared server update procedure](v1.0.1.md#shared-server-update) explains the existing explicit replacement process. Finish connected work before replacement and verify the actual executable and server version. Extraction does not replace a running server or migrate a profile. Do not delete existing databases or authentication files for recovery. Final 1.1.0 asset names and checksums must be recorded only after the actual release assets are built and verified.

### Validation and known limitations

Generation publication is limited to 64 retained generations and 1 GiB of logical generation files, including the proposed generation. Each stage is limited to 32 MiB and 10,000 entries; at most two failed stages are retained before new work is blocked. Blocking preserves the previous current generation. These bounds do not reserve physical disk space or guarantee power-loss durability of Windows directory entries. Recovery procedures require their own execution checks before release. Direct file access by another process with the same operating-system privileges is outside the host reader's same-handle integrity check.

Native 1.1.0 verification is in progress. The link-owner and configuration-target changes have not yet completed native regression or joint Desktop verification. Creating Windows file symlinks in the current test session returned error 1314; the original symlink contention red/green test has not run. Historical source-import evidence of 50 runs, 49 passes and one skipped case, and the earlier five cache-policy passes on the 1.0.1 development candidate, cover those respective test conditions only; they are not final 1.1.0 validation. Real-provider/model cache behavior, sustained workload effects, actual Desktop integration, final binary/package checks and independent audit require their own results. Java migration, new multi-vendor login, automatic updater and installation migration are outside this scope.

## 한국어

### 개요

이 문서는 Windows x86-64 1.1.0 후보의 발행 전 소스 초안입니다. 네이티브 시험과 Desktop 공동 통합이 진행 중입니다. 최종 소스 식별자, 실행 파일, 패키지, 독립 감사와 발행은 아직 확정되지 않았습니다. 과거 시험을 1.1.0 릴리스 검증으로 간주하지 마십시오.

### 변경 사항

* 인덱스 작업 조각과 의존 항목이 선택 문맥을 결정합니다. 무관한 상세 내용을 모델의 활성 입력에서 제외해도 원문은 권한에 따른 조회를 위해 보존합니다. 요청 전용 탐색 정보는 선택된 이력 뒤에 놓여 탐색 정보가 바뀌어도 안정적인 접두부를 유지합니다.
* 인덱스 포커스가 있으면 선택 문맥이 입력 예산을 사용합니다. 선택 항목이 모델 한도를 초과하면 필수 근거를 요약으로 대체하지 않고 한도 오류를 알립니다. 다시 시도하기 전에 더 작은 원문 조각을 조회하거나 무관한 상세 내용을 제외하십시오.
* 실험적 `thread/context/read`는 기존 연결 및 실행 인스턴스 접근 검사 아래 로드된 스레드의 본문 없는 메타데이터를 반환합니다. 페이지는 `snapshotId`로 한 세대에 묶이며 `staleContextSnapshot`이면 처음부터 다시 조회합니다. 직렬화된 각 페이지는 65,536바이트 이하여야 합니다. 상주 데이터의 UTF-8 직렬화 바이트, 로컬 토큰 추정치와 제공자 보고 사용량을 구분합니다. 이용할 수 없는 값은 null 또는 명시적 미확인 상태이며 보관 크기를 0으로 추정하지 않습니다.
* `hooks/list`는 현재 스레드에 설치된 런타임과 설정 검색을 구분합니다. MCP/hook 설정 갱신은 활성 런타임 및 정책 경계를 따릅니다. 요청 확인만으로 MCP 서버 준비 완료를 뜻하지 않습니다. Hook stdout과 stderr는 각각 1 MiB로 제한하며 초과 시 오류를 반환합니다.
* 제공자 캐시 정책은 선택 사항입니다. 지원하는 Responses 호환 제공자에 대해 `[model_providers.<id>.capabilities.prompt_cache]`에서 `kind = "implicit"`과 `ttl = "30m"` 또는 `"12h"`를 지정할 수 있습니다. 지원되는 경우 명시적 대안으로 `kind = "legacy"`와 `retention = "in_memory"` 또는 `"24h"`를 선택할 수 있습니다. 정책을 지정하지 않으면 기존 전송 동작이 유지됩니다. 새로운 벤더 로그인이나 다른 전송 프로토콜을 추가하지 않습니다.
* 요청 TTL과 보고된 캐시 활동은 제공자의 지원, 적용 또는 보존을 확인하지 않습니다. `minimumValidUntil`, 실제 적용 TTL, 개별 조각 TTL과 서버 확정 만료는 미확인 상태로 유지합니다. TTL 만료는 원문을 삭제하거나 권한과 필수 선택을 변경하지 않습니다.

* 선택 항목 `requestSizes`는 마지막으로 준비한 sampling prompt의 input·기본 지침·독립 tools 필드·출력 스키마에 대한 JSON 바이트 수 네 개를 제공합니다. 서버가 합계와 준비 당시의 history/index 리비전을 함께 반환합니다. input에 포함된 증분 도구 정의는 input 크기에 포함됩니다. 이 관측은 화면의 최신 이력보다 이전일 수 있으며 제공자 정규화, 전송 봉투, delta 요청, 과금 토큰이나 전송 성공을 측정하지 않습니다. 크기 계측을 위해 본문 사본을 추가 보관하지 않습니다.
* TUI MCP 등록의 수명은 연결과 해당 대화의 구독에 묶입니다. 진행 중 호출의 수명을 보존하고 대기 중 교체는 안전한 런타임 경계에서 적용합니다. 비밀이 아닌 등록 식별자로 적용된 등록과 실제 게시·연결된 MCP 상태를 연결합니다. 대기·적용·준비 상태를 구분하며 사용자·관리 설정, 인증, 승인과 도구 이름 공간의 검사를 유지합니다.
* 후보는 마우스로 여는 HTTP(S) 링크에 `--terminal-link-owner=tui|host`를 지원합니다. 기본값은 `tui`이며 터미널 호스트가 실제로 링크를 열 때에만 `host`를 지정합니다. 파일 링크와 프로그램이 인증을 위해 여는 URL은 기존 경로를 유지합니다. 버전 문자열만으로 지원 여부를 판단할 수 없습니다.
* 설정 쓰기는 같은 작업에서 실제 저장한 직렬화 문서로 반환할 user-layer 버전을 계산합니다. 협력하는 writer는 지원되는 symlink 경로를 같은 대상으로 해석해 잠그고 현재 읽은 내용으로 버전을 검사합니다. 빈 계층의 경계와 Windows 경로의 대소문자 동작은 유지합니다. 시작한 blocking 쓰기는 호출자가 취소해도 저장이 끝날 때까지 잠금을 보유합니다. 비협력 외부 편집기와 검사 후 경로 교체는 보장 범위에 포함되지 않습니다.
* 메모리 통합은 선택 입력을 크기가 제한된 stage에서 준비한 뒤 기존 저장소의 lease·인가·입력 검사를 통과한 세대를 발행합니다. 호스트 reader는 한 세대를 캡처합니다. 초기화는 현재 발행 참조를 제거하고 원본 노트·관리 marker·복구 세대는 보존합니다. 관리 상태의 읽기 실패를 이전 legacy 요약으로 조용히 대체하지 않습니다. 세대 ID는 현재 캡처한 세대를 식별하며, 다른 reader의 과거 세대 참조 해제나 모델의 의미적 주장 정확성을 증명하지 않습니다.

Core 내부 특수 승인 흐름에는 Core가 발행한 출처 표시와 기존 요청 검사가 모두 필요합니다. 외부 MCP 메타데이터로는 해당 출처를 선택할 수 없습니다. 출처가 누락된 Core 1.0.1 요청은 미확인으로 처리하며, 이를 새 클라이언트의 특수 승인 지원 근거로 추정하지 않습니다. 일반 form과 API의 기존 의미는 유지합니다. 사용 전에 클라이언트와 Core 조합의 지원 여부를 확인하십시오. 설치나 프로필 이전은 자동으로 수행되지 않습니다.

### 시작과 복구

1.1.0 TUI 후보의 `/context inspect`는 최대 25개 조각으로 구성된 메타데이터 페이지 하나를 조회합니다. `/context inspect next`는 같은 스냅샷의 다음 페이지만 요청하며 전체 이력을 자동 조회하지 않습니다. 페이지가 64 KiB를 넘으면 `/context inspect small`로 조각 하나부터 다시 조회할 수 있습니다. 단일 조각도 한도를 넘으면 표시할 수 없다는 오류를 알립니다. `/context cancel`은 조회 결과의 표시를 취소하며 이미 보낸 요청은 실제로 끝나거나 연결이 종료될 때까지 제한된 대기 슬롯을 유지합니다. 기존 문맥 크기 조회·초기화·정수 설정과 구분합니다.

검증된 릴리스의 완전한 패키지에서 `bin` 폴더, 패키지 메타데이터와 helper를 함께 사용하고 이전 전체 패키지를 복구용으로 보관하십시오. 기존 명시적 교체 방식은 1.0.1 [공유 서버 업데이트 절차](v1.0.1.md#공유-서버-업데이트)를 참고하십시오. 교체 전에 연결된 작업을 마치고 실제 실행 파일과 서버 버전을 확인하십시오. 압축 해제만으로 실행 중 서버를 교체하거나 프로필을 이전하지 않습니다. 복구를 위해 기존 데이터베이스나 인증 파일을 삭제하지 마십시오. 최종 1.1.0 자산 이름과 체크섬은 실제 빌드와 검증 이후에만 기록해야 합니다.

### 검증과 제한

발행 상한은 새 세대를 포함한 보존 세대 64개와 generation 파일의 논리 크기 1 GiB입니다. 각 stage는 32 MiB와 10,000항목으로 제한하며 실패 stage는 최대 두 개를 보존한 뒤 새 작업을 차단합니다. 차단 시 이전 현재 세대는 보존합니다. 이 상한은 실제 디스크 공간을 예약하거나 Windows 디렉터리 항목의 정전 내구성을 보장하지 않습니다. 복구 절차는 릴리스 전 별도 실행 검증이 필요합니다. 같은 운영체제 권한을 가진 다른 프로세스의 직접 파일 접근은 호스트 reader의 동일 handle 무결성 검사 범위 밖입니다.

1.1.0 네이티브 검증은 진행 중입니다. 링크 소유권과 설정 대상 변경의 네이티브 회귀 및 Desktop 공동 검증은 아직 완료되지 않았습니다. 현재 시험 세션에서 Windows 파일 symlink 생성은 오류 1314로 실패했으며 원래 symlink 경합의 red/green 시험은 실행하지 못했습니다. 기존 소스 가져오기 시험 50회 중 49회 통과·1회 건너뜀과 앞선 1.0.1 개발 후보의 캐시 정책 5개 통과는 각각 해당 시험 조건의 근거일 뿐 1.1.0 최종 검증이 아닙니다. 실제 제공자·모델 캐시 동작, 지속 부하 효과, Desktop 실통합, 최종 실행 파일·패키지 검사와 독립 감사는 별도 결과가 필요합니다. Java 이전, 새로운 멀티벤더 로그인, 자동 updater와 설치 이전은 이번 범위에 포함되지 않습니다.

### 소스와 무결성

`CURRENT_SOURCE.json`, 대응 파생 소스, AGPL-3.0-or-later, 원 저작권과 제삼자 고지를 보존합니다. [변경 고지](../../MODIFICATIONS.md), [소스 가져오기](../source-import.md), [라이선스 안내](../../LICENSING.md)를 참고하십시오. 최종 릴리스 근거에는 실제 소스 리비전, 빌드 설정, 자산 해시, 검증 및 발행 결과를 기록해야 합니다.
